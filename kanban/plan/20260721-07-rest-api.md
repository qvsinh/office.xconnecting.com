# 07 — REST API for AI Agents (`/api/v1`)

**Goal:** A Bearer-token REST API so an AI agent (using a user's API key) can read
projects and CRUD tasks, scoped to that user's memberships. Tested.

**Depends on:** 01 (ApiKeyModel, access helper), 04, 05.

## Files
- Create `app/Filters/ApiKeyFilter.php` (alias `apikey`).
- Create `app/Controllers/Api/V1/BaseApiController.php` (shared JSON envelope +
  resolved `$this->apiUser`), `Me.php`, `Projects.php`, `Tasks.php`.
- Modify `app/Config/Filters.php` (register `apikey` alias), `Routes.php`
  (an `api/v1` group with `['filter'=>'apikey']`; CSRF does NOT apply — token auth).
- Modify `app/Config/Cors.php` if needed (allow the API path). Keep default-safe.
- Tests: `tests/feature/Api/V1/ApiTest.php`.

## Auth (ApiKeyFilter)
- Read `Authorization: Bearer <token>` (fallback `X-Api-Key`). Missing/blank →
  401 JSON `{error:'unauthorized'}`. Resolve via `ApiKeyModel::resolve($token)`;
  null → 401. On success set the resolved user id into a request-scoped place the
  controllers read (e.g. `service('request')` attribute, or re-resolve in the
  BaseApiController via a shared method). Simplest: filter stashes user id in a
  static/`Services` or sets `$request->apiUserId` — CI4: use
  `Services::request()` is shared; store via `session()` is wrong (no session).
  Use a tiny singleton: `App\Libraries\ApiContext::set($userId)` /
  `::userId()`. Filter validates scope for writes: POST/PATCH/DELETE require the
  key `scopes` to include `write` → else 403.

## Endpoints (all JSON, consistent envelope `{data, error, meta}`)
```
GET    /api/v1/me                      → current user + counts
GET    /api/v1/projects                → projects the key's user can access
GET    /api/v1/projects/{id}           → project + columns
GET    /api/v1/projects/{id}/tasks     → tasks (filter ?column_id, ?assignee_id, ?priority)
POST   /api/v1/projects/{id}/tasks     → create task {title, description?, priority?, assignee_id?, due_date?, column_id?}
GET    /api/v1/tasks/{id}              → one task
PATCH  /api/v1/tasks/{id}              → update fields
DELETE /api/v1/tasks/{id}              → soft delete
```
- Every handler re-checks access via the access helper against
  `ApiContext::userId()` (NOT the web session) — read needs `project_role`,
  write needs `can_edit_project`. This is the same IDOR guard as the web side.
- Input validated with CI4 Validation; 422 on failure with field errors.
- 404 for unknown/inaccessible ids (don't leak existence).

## Notes
- No CSRF on `/api/v1` (stateless token auth) — the routes group must not add the
  `csrf` filter. Ensure global CSRF stays off (it is; only per-route `csrf`).
- `ApiContext` is a plain final class with a static `?int $userId` — ponytail:
  a request is one process; a static is the minimal correct carrier. Reset in
  the filter's `before()` each request.

## Tests
- No token → 401; bad token → 401; read-scope key doing POST → 403.
- Valid key: GET /me, list projects (only the user's), create+get+patch+delete a
  task in an accessible project; a task in an inaccessible project → 404.
- `last_used_at` stamped on use.
